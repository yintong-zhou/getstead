# M4a Property and condominium — implementation plan (decisions confirmed, awaiting Codex review)

Spec (PROJECT.md): properties with estimated value and linked mortgage; condominium with regular instalments, balancing payments, approved extraordinary works and due dates; "Home and property doesn't duplicate data: condominium instalments create transactions in cash flow, and property values feed into net worth." Base: `main` after PR #6 (M3). Do not build before Codex approves the plan and the owner authorises the build.

**Slice.** M4a is properties and condominium only. Deferred to later slices (owner, 2026-11-20): utility bills, subscriptions, rental income (`RecurringTemplate` is expense-only, see Out of scope), encrypted attachments, cron/email reminders.

Facts the build must respect: product name **getstead** (tables `stead_*`, cookie `getstead_session`); mobile navigation labels must fit without ellipsis, with the visible text contained in the accessible name (WCAG 2.5.3, enforced by `components/dashboard-copy.test.ts`); migration timestamps must sort after `20261123100000` (this plan uses `20261124090000_property`); advisory lock key 3 is taken by investments, **this milestone uses key 4**.

## Decisions (owner confirmed 2026-11-20)

1. **Valuation history.** A property has dated estimated values (`PropertyValuation`, one per property and date), the same pattern as `PriceQuote`. The value at date D is the latest valuation on or before D; with none, the property contributes 0 and is flagged "no valuation". Values are the owner's own estimates, labelled as such in the UI.
2. **Two different shares, both modelled.** (a) `ownershipBps` on the property: the share of the property the owner holds, 1 to 10,000 basis points (10,000 = 100%), scaling its value in net worth. (b) **Millesimi** (condominium thousandths): `CondoTable` rows per property, each with a label (for example General, Stairs, Lift, Heating), the unit's millesimi and the building total (default 1,000, integers, `1 <= unit <= total`). Millesimi split building costs and weigh votes at assemblies; they never enter net worth. A pure helper gives the owner's share of a building-wide amount: `round-half-up(totalCents × unit / total)` in bigint, and the voting weight `unit / total`. Rejected: one combined percentage, because the two shares differ (a co-owned flat has 50% ownership and its own millesimi).
3. **Mortgage is an informational link.** `mortgageAccountId` points to an existing `DEBT` account of the same user (composite FK, validated type, unique per user so one loan is not linked to two properties). Net worth already counts that account as a liability, so **liabilities do not change** and nothing is counted twice. The property card shows equity = value share minus the account's current debt balance, computed for display only. A type change of that account away from `DEBT` while linked is refused (409), like the M3 guard.
4. **Instalments reuse the recurring engine.** `CondoSchedule(propertyId, templateId)` links an existing `RecurringTemplate` (expense) to a property. Confirming, matching or skipping an instalment stays in the existing Recurring flow (`resolveOccurrence`), so a movement is booked exactly once. The property page lists the linked schedules with their next due date and links to Recurring. `createTemplate` gets an optional client argument so the template and its link are created in one transaction (behaviour-preserving; existing M1 tests cover it). Rejected: a second recurrence engine.
5. **One-off charges are a dedicated table.** Balancing payments (conguagli) and approved extraordinary works are dated, not periodic, so they do not fit `RecurringTemplate`. `CondoCharge` holds a **required `propertyId`**, `kind` (`BALANCING | EXTRAORDINARY`), an encrypted `title`, `dueDate`, `amountCents` (> 0 and **at most `MAX_CENTS` = 1,000,000,000, the existing movement limit**, because settling books it as one movement; Prisma `Int`, the movement CHECK and `Reader.cents` all stop there), optional `approvedOn` (assembly date), optional `tableId` with `buildingTotalCents` (the building-wide amount, up to 1e11, kept so the computed millesimi share can be shown next to what was actually invoiced), `voidedAt`, and `movementId` (set when settled). Settling books one expense movement in an account chosen by the caller, exactly once (row lock on the charge, unique `(userId, movementId)`). Reopening a settled charge unlinks it and leaves the movement booked, as `reopen` does for occurrences.
   **A settling movement is protected like one that settles an occurrence.** Today only `occurrence` links are guarded (`server/cash-flow/movements.ts`: select and DTO at lines 26 and 56, void at 201, edit at 237, pair at 326, candidates at 393 and 419). M4a extends every one of them to a charge link: the movement select and DTO expose the link (`chargeLinked`), void is refused (409 `linked`), an edit that changes the account or turns the movement into income is refused, pairing into a transfer is refused, and the pairing and match candidate queries exclude it. **Exclusive linkage:** `resolveOccurrence` action `match` refuses a movement that already settles a charge (409 `already_linked`); both paths check under `lockMovements`, so a movement can never settle a charge and an occurrence at once (two link tables cannot share a unique key, so exclusivity is enforced by this check under the movement lock, not by a constraint). The UI shows the link and asks to reopen the charge first. A balancing **credit** (refund) is not a charge in v1: enter it as a normal movement.
6. **Sale date.** `soldOn` (nullable) on the property: the value counts for dates before `soldOn`. Archiving only hides the property from lists, so history is not rewritten. The sale proceeds are a normal movement entered by the owner.

## Model

- `Property`: `id`, `userId`, `name` (unique per user), `kind` (`PRIMARY_RESIDENCE | SECOND_HOME | RENTAL | LAND | OTHER`), `ownershipBps` (default 10000, CHECK 1..10000), `mortgageAccountId` (nullable), `soldOn` (nullable date), `archivedAt`.
- `PropertyValuation`: `id`, `userId`, `propertyId`, `asOf` date, `valueCents` BigInt (CHECK 0 < value <= 1e12). Unique `(userId, propertyId, asOf)`.
- `CondoTable`: `id`, `userId`, `propertyId`, `label`, `unitMillesimi` Int, `totalMillesimi` Int (default 1000). Unique `(userId, propertyId, label)` and `(userId, propertyId, id)` (target of the charge's composite key), CHECK `1 <= unit <= total <= 100000`.
- `CondoSchedule`: `id`, `userId`, `propertyId`, `templateId`. Unique `(userId, templateId)`: a template belongs to at most one property.
- `CondoCharge`: as in decision 5. Foreign keys: `(userId, propertyId)` to the property, and `(userId, propertyId, tableId)` to `CondoTable(userId, propertyId, id)`, so a table must belong to the charge's own property (a table-free charge has a null `tableId` and is still attributed to its property). CHECKs: `amountCents` between 1 and 1e9, `buildingTotalCents` between 1 and 1e11, `tableId` and `buildingTotalCents` both set or both null, `buildingTotalCents >= amountCents` when set.
- Foreign keys include `userId` like M1 to M3 (`(userId, id)`), `ON DELETE RESTRICT`. `@@unique([userId, id])` on each model, `stead_*` table names. Every query is scoped by `userId`. Grants in `db/grant-runtime.sql`: SELECT and INSERT everywhere; UPDATE only on the named editable columns; DELETE only on `stead_property_valuations`, `stead_condo_tables` (blocked by RESTRICT while charges use them) and `stead_condo_schedules`; no DELETE on properties or charges (archive and void).
- Free text (charge titles) is encrypted with `encryptText` and a new context `chargeContext(id)` in `server/cash-flow/text-crypto.ts`. Property names, table labels and kinds are short non-sensitive labels, stored in clear like account and instrument names.

## Pure calculation (`server/property/calc.ts`, node:test, synthetic data)

- `valueAt(valuations, asOf)`: latest valuation on or before the date, else none.
- `shareValueCents(valueCents, ownershipBps)`: bigint `round-half-up(value × bps / 10000)`.
- `propertiesAt(properties, valuations, date)`: per property and total of `shareValueCents`, skipping properties sold on or before the date, with a `noValuation` flag. All sums in bigint; `toSafeCents` (reused from `server/investments/calc.ts`) is the only way into numbers.
- `millesimiShareCents(totalCents, unit, total)` and `votingWeight(unit, total)`.
- `equityCents(shareValue, debtBalanceCents)`.
- Bounds: valuation and building-total columns are capped (1e12 and 1e11 cents) and payable charges at 1e9 cents, at most 50 properties, 2,000 valuations and 2,000 charges per user, so every sum stays below `Number.MAX_SAFE_INTEGER` (50 × 1e12 = 5e13).
- Tests: share rounding (odd cents, 3333 bps), 100% and 1 bp, latest-valuation selection and ties on date, no valuation, sold property drops out exactly on `soldOn`, millesimi rounding (1000 total and a 1042 total), a share that rounds to 0 is allowed, overflow guard.

## Service, API, UI

1. **Schema and migration** `db/migrations/20261124090000_property/migration.sql`, grants, `db/schema.prisma`. Apply to Neon only with explicit approval.
2. **Service** `server/property/service.ts`: CRUD for properties, valuations, tables, schedules and charges (void instead of delete for charges); `settleCharge`, `reopenCharge`; `getOverview(userId, now)` (properties with value share, equity, tables, schedules with next due date, charges split pending/settled). Validation through `Reader` in `server/cash-flow/validate.ts`; errors through `ApiError`, `conflict`, `notFound`. No amounts in logs.
   **Write serialization:** every write takes `pg_advisory_xact_lock(hashtextextended(userId, 4))` first, then locks rows in this fixed order: account (**`FOR NO KEY UPDATE`**, never `FOR UPDATE`, because movement inserts hold `KEY SHARE` on the account through the foreign key; this is the deadlock Codex found in M3), property, charge or template, movement. Files outside `server/property/` that change: `server/cash-flow/movements.ts` and `server/cash-flow/recurring.ts` (charge-link guards, exclusive linkage, `createTemplate` client argument), `server/cash-flow/text-crypto.ts` (`chargeContext`), `server/cash-flow/catalog.ts`, `server/net-worth/*`. `updateAccount` returns 409 when it would change a linked mortgage account away from `DEBT`.
3. **Net worth hook.** `getNetWorth` loads properties and valuations in the same RepeatableRead transaction and adds `propertiesCents` to assets in **both** `netWorthAt` and `monthlySeries` (`server/net-worth/calc.ts`), exactly as holdings were added in M3. It returns `propertiesCents`; the Net worth page shows a "Properties (estimated value, your share)" row so account rows plus holdings plus properties add up to the total. Tests: extend the history-parity test, require the final series point to equal the current totals, mortgage on a `DEBT` account leaves liabilities unchanged, a sold property drops out of the series from `soldOn`.
4. **API** `app/api/property/**` through the existing `api()` wrapper: `properties` (GET list/overview, POST), `properties/:id` (PATCH, including `archived` and `soldOn`), `valuations` (GET, POST, PATCH value, DELETE), `tables` (POST, PATCH, DELETE), `schedules` (POST creates the template and link; DELETE unlinks), `charges` (GET, POST, PATCH with `voided`, and `{ "action": "settle" | "reopen" }`). DTOs never expose `userId`. Invalid values return 422 (`value_out_of_range` for caps), conflicts 409.
5. **UI** page `/[locale]/property` (EN and IT): property cards with value share, valuation date, equity, a "no valuation" state; add-valuation quick entry; millesimi tables with the unit's weight (for example "85 / 1000 = 8.5% of votes"); instalment schedules with next due date; charges list with a pending/settled split and a settle form (account picker); a calculator that pre-fills a charge amount from a building-wide total and a table. Copy in `components/property/copy.ts`. Nav item "Property" / "Casa": the mobile bar goes to **8 columns**; labels stay visible from 390 px up and below that the items show icons with `aria-label` and visible focus (the M3 threshold of 360 px no longer fits); `.page` bottom clearance re-checked; the WCAG 2.5.3 unit test extended. Every number shown as an estimate carries the label "owner's estimate, not an appraisal". Glass style and brand guidelines, works at 320 px.
6. **Tests**: calc unit tests; integration suite `server/property/postgres.integration.ts` added to `test:postgres` for user isolation (another user's mortgage account, template and table are rejected), constraints, runtime-role grants, exactly-once settle under concurrency (two settles, one wins), settle then reopen then settle, settling at the 1,000,000,000-cent boundary succeeds and 1,000,000,001 is rejected with 422, a settling movement cannot be voided, turned into income, moved to another account or paired into a transfer (409 `linked`) until the charge is reopened (including concurrent reopen versus edit), the same movement cannot settle a charge and match an occurrence (both orders), a table of another property of the same user is rejected for a charge, table-free charges work, mortgage type-change guard, schedule creation atomicity, a concurrency regression covering a B→A transfer against a property write that locks accounts (must not block or deadlock), net worth with properties; plus the existing M1 recurring and movement tests green after the `createTemplate` and movement-guard changes (the new guards are additive; behaviour for occurrence links is unchanged).
7. **Docs**: README section; handoff.

## Out of scope for M4a

Utility bills, subscriptions, **rental income** (`RecurringTemplate` is expense-only: positive amount booked negative, expense categories, outflow-only matching; income needs a generalisation of M1 recurring code, planned with the rent slice), encrypted attachments (bill PDFs, meeting minutes), reminders, cron and email, OCR, automatic valuation, property tax and cadastral calculations (IMU, TARI), co-owner management, condominium balance sheets (rendiconti) and per-unit budgets, balancing credits as charges, goals and projections.
